## 非逐字近似重复：去重后对账删除集

<!-- 原编号 §2.31 · 脱敏风险 低 -->

**问题**：在文本处理与去重流程中，机械去重可能会误删非逐字相同的内容，需要对删除集进行对账，以确保语义得到完整保全。

**机制**：逐字检测仅用于候选发现，不能作为语义保全的最终证明。在机械去重后，必须核对全部删除行，列出未在唯一正本中逐字出现的内容，并逐项证明其现存承载位置，否则予以恢复。需先确认重复是否由验证契约强制要求；若原契约要求逐字摘录而目标调整为单正本，应改为指针有效性契约并保留失效反例，而非保留副本或进行静默检查。此方法用于补充既有的保全机制。

**证据**：实测：逐字阈值≥40字符找到数十条重复行，实际删除数十行，其中不到一成非逐字相同；检测量数千字符，实际删除数千字符。针对版本戳重复行，检查强制其逐字相等，删除后触发验证失败，修正方法为调整验证契约而非取消验证。

**判据**：在对账时，核对范围是全部已删除内容，还是仅限疑似重复的内容？每一条非逐字的删除内容，当前承载位置在哪里？该重复要求是否被检查契约强制规定？

**脱敏说明**：仅将具体执行日期和精确读数替换为相对量级，核心机制、判据逻辑及阈值参数完整保留，未引入任何原文之外的信息。

## 行号与字符偏移属于不同坐标系：文本切片必须统一坐标

<!-- 原编号 §2.71 · 脱敏风险 低 -->

**问题**：按行遍历文档时取得行号，却又用该行号作为字符偏移切取字符串，会把两个不同的坐标体系混为一谈。切片结果通常仍是合法文本，不会立即报错，却可能静默丢失章节、元数据或代码块；如果被修改的是唯一副本，损失不可逆。

**机制**：行号表示行序列中的位置，字符偏移表示整个字符序列中的位置；只有每行恰好包含一个字符时，两者才可能相等。按行处理应使用 `lines = text.splitlines(keepends=True)` 后通过 `lines[a:b]` 切片；按字符处理则应全程使用 `text.find()` 或 `text.index()` 获取位置，不能混用。切片后还应分别核对标题数量、元数据边界和格式校验结果，这三项是相互独立的断言，不能用其中一项替代其余两项。

**证据**：实测：拆分一份约六百余行的说明文档时，先用 `splitlines()` 取得行号 `i`，随后用 `text[:i]` 切取字符串，即把行号当成字符偏移。结果原约六百余行文件被截成不到原行数六成，frontmatter 在 `description` 中间断开，步骤 0、1、2 以及步骤 3 的前半部分全部丢失；由于没有备份，只能从版本控制上游仓库重新拉取。当时误以为“第 i 行”和“第 i 个字符”是同一个位置，而两者只有在文件每行恰好一个字符时才相等。另一处同类错误是：将 `sed` 取得的某一行区间直接传给按字节处理的 `dd`。这类错误尤其隐蔽，因为切片结果永远不会报错：`text[:i]`（行号值被误当字符偏移）是合法字符串，写回后也是合法 Markdown，只会静默缺失内容，通常几小时后才会发现某个小节不见了；如果操作对象是唯一副本，损失将不可逆。

**判据**：满足以下三项才算合规，任一项缺失即视为违规，不允许先操作后补救：1. 先备份：执行 `cp f f.bak`，或将文件提交到版本控制系统；破坏性操作前必须已有可回滚的备份，不允许“先试试看”。2. 坐标系统一：按行操作时使用 `lines = text.splitlines(keepends=True)`，再通过 `lines[a:b]` 切片；按字符操作时，全程使用 `text.find()` 或 `text.index()` 获取位置，禁止混用行号与字符偏移。3. 切片后核验结构：核对标题 `##` 的原有数量与当前数量，确认 frontmatter 的 `---` 成对闭合，并运行该文档格式对应的校验器；这三项自查必须分别作为独立断言执行，不能互相替代。判定前还应确认：`i` 来自行循环还是字符搜索，操作对象是否为唯一副本，备份位于何处，以及用什么证据证明结构没有丢失。若切片后文件行数明显小于预期、已知小节找不到，或 frontmatter 或代码块未闭合，应立即停止并回滚，不要尝试直接补写。

**脱敏说明**：已删除具体日期、版本号、精确行数对、精确字符偏移示例和具体行区间，保留的机制、判据与小样本步骤编号不构成唯一执行指纹。

## 就地修改文档的脚本：非目标行必须原样写回，并落实为断言

<!-- 原编号 §2.76 · 脱敏风险 低 -->

**问题**：就地修改文档的脚本需要按条件更新指定行或字段，但改行逻辑与写行逻辑分离时，非目标行可能被静默删除；脚本仍会输出修改处数并以 0 退出，人工检查前看不出内容丢失。另一类失败发生在拼接表达式中：输入文件的前缀或后缀区间没有写回，目标内容虽然替换成功，整段原文却随之消失。脚本打印的前后计数已经异常，如果执行者没有据此立即停止，改写仍会完成。除此之外，编号唯一性检查可能只识别一种标题格式，从而漏掉跨卷重号；成功提示也可能被硬编码，实际没有执行对应检查时仍宣称检查通过。

**机制**：在按行读取的循环中，“跳过当前行”和“原样保留当前行”是两件不同的事。continue 会跳过本轮剩余语句；如果 append 位于 continue 之后，非目标行就既不会被修改，也不会被写回。任何“按行读、按条件改、按行写”的脚本，只要改行逻辑和写行逻辑不在同一条代码路径上，都可能在“不变性”一侧静默丢行。脚本自述“改了若干处、exit 0”只证明它动了打算动的行，不证明它没有动不打算动的行。

第二类失败的机制不在单个条件分支，而在拼接表达式：只要输入文件的某个区段没有出现在结果中，缺失区段就等同于被定义成删除集。因此，就地改写应统一写成 lines[:i] + 新内容 + lines[i:]，不能只取目标行再拼接新内容。写前和写后还应分别运行断言：写前检查原始摘要值和结构计数，写后检查非目标前缀逐行相等、新增或改写内容已经就位、差异类型符合预期。文档中的纪律只能降低复发概率，断言中的纪律才构成防线；动手前建立的完整备份则提供回滚点。

编号唯一性检查如果只识别 Markdown 标题，而条目采用另一种标题形态，就无法发现跨卷重号。主文件加一个分卷可以是既定设计，两个分卷各出现同一编号才是缺陷。补充检查后必须运行负对照，确认真正制造重号时检查会失败，不能仅凭“已经添加代码”认定检查有效。解析检查对象时，附注还可能干扰编号或条目计数，因此附注应另起一行，解析范围应收窄到第一个句号或附注标记之前。

成功信息中的每个限定词也必须由当轮实际执行过的检查推导，不能手写。检查是否存在、是否实际运行，应由明确的标志位或执行结果决定；否则删除检查后，守卫仍可能返回成功并输出不真实的覆盖范围。

**证据**：首次实测发生于一次深夜至凌晨。一个就地更新 Markdown 目标字段表的脚本使用 for line in fh: 遍历文件：非目标行执行 continue，目标行则修改字段并重建该行；原样写回统一放在循环末尾的 new_lines.append(line)。由于 continue 连 append 一起跳过，另一张同名表中的十余行被整体删除。这些行的首列脚本名与目标表相同，但值列不是目标指纹。脚本仍打印“改写数处”并 exit 0，完全没有暴露丢行；执行后人工 diff 才发现问题。回滚后把 continue 改为 pass，让非目标行继续经过原样写回路径，并且只在值列能够按预期类型解析时才执行改写。

随后的第二类实测中，表达式写成了 new = lines[i] + E1 + E2 + lines[i+1:]，而 lines[:i] 从未拼回。结果是一份本应拆成两百余段的总目录被拆成个位数段，行数统计只剩数行，开头两百余行整段消失，脚本仍然 exit 0。脚本已经打印出拆分前的段数是两百余、拆分后只有个位数，但执行者看到这个落差后没有立即停止。第一类规则写入规则文档仅隔极短时间，随后仍发生了第二类错误，说明文档规则本身不能替代断言和回滚点。该次恢复依靠动手前建立的整份备份；恢复后摘要值与原文件逐字节复现。写前、断言写后各一组检查的方案实际兜住了后果。

另一次第三类实测发现，同一条目同时存在于两个分卷。编号唯一性采集只识别 ^#{2,3} 2.N 形式的 Markdown 标题，而另一分卷的条目使用以 **§2.N 开头的粗体小节，因此跨卷重号没有被发现，检查仍报告“编号唯一”。补充跨卷重号检查后，通过负对照确认真正制造跨卷重号时检查会报红。补充检查过程中又出现同族误报：给卷头加入“已并入”说明后，附注中的编号被计入待检查条目数，造成数条检查结果误报为多出一条；将清单解析范围收窄到第一个句号或附注标记之前后恢复，并把附注改为另起一行。

另一次第四类实测还发现，成功信息中的“含跨卷重号”等限定词是硬编码字符串。负对照中删除跨卷重号检查，再加入真正的跨卷重号，守卫仍然 rc=0，并继续打印“含跨卷重号”。改为根据“该检查是否真的运行”的标志位推导成功信息后，删除检查会使成功信息随之变化；一致性验收脚本的逐字节比对捕获了这一变化，实测 rc=1。

**判据**：以下要求全部满足才算合规，任一项不满足都应视为存在违规风险：
1. 改行逻辑和写行逻辑是否位于同一条代码路径上？所有非目标行是否都确实经过 append 并原样写回？
2. 是否使用 diff 验收过差异类型，即 c 表示变更、d 表示删除？不能只相信脚本自述的“改了几处”；只信自述等于把判断权交给了脚本。
3. diff 中匹配 ^[0-9,]+d 的纯删除行数是否为 0？如果不是 0，立即回滚。
4. 拼接表达式中是否包含输入文件的每一个区段？lines[:i] 与 lines[i:] 缺少任何一段，都意味着正在定义删除集。就地改写一律使用 lines[:i] + 新内容 + lines[i:]。
5. 是否逐个核对脚本打印的前后计数，包括 pre/post split 和 pre/post md5？只要有一个与预期不符，就是立即停止、检查当前文件状态的信号，不能按“差不多”继续执行。
6. 这条要求是只写在注释里，还是已经落实为可执行断言？写前和写后是否分别检查了非目标行逐行相等、目标内容就位以及差异类型？只有断言才算防线。
7. 同一编号是否出现在两个分卷中？跨卷编号唯一性检查必须实际运行；补充检查后必须另跑负对照，确认真正出现跨卷重号时能够失败，不能以“加了代码”等同于“检查有用”。主文件加一个分卷可以是设计，两个分卷各有一份同一编号才是缺陷。

另有一条适用判据：成功信息里的每一个限定词是否都由当轮真正执行过的检查推导？限定词不得手写，检查不存在或未运行时，成功信息必须相应变化。

**脱敏说明**：已将具体日期、精确行数及计数等来源指纹替换为相对量表述，机制与判据逻辑均原样保留，未引入原文外的新结论或占位符。

## 判据要锚定到「那一行」，不能全文搜关键词

<!-- 原编号 §2.84 · 脱敏风险 低 -->

**问题**：在编写断言规则时，如果采用全文搜索关键词的方式来判断内容是否存在，一旦文档的其他位置合法地包含了该关键词，该断言就会永远成立（恒真），从而无法发挥任何拦截作用。

**机制**：为断言编写校验逻辑时，应将检查范围精确锚定到目标行或特定字段，而非在全文中进行宽泛的关键词搜索。若仅进行全文搜索，文档其他位置的合法内容会导致搜索结果恒真；将搜索范围收敛为仅检查目标所在的具体行后，校验机制才能正常生效。该机制与其他校验规则形成互补：其他规则关注值是否同步更新，本规则关注检查的位置是否正确。

**证据**：在一次系统自检中，新增了一条“若目标配置允许逐套主题重配，则必须写明 ≥60° 约束”的断言。最初实现为在全文中搜索 `'60°'`。通过变异测试注入“删除目标配置行中的 ≥60°”时，该断言未触发拦截，返回 rc=0。原因是文档的另一处合法内容中也包含了 `60°`，导致全文搜索结果恒真。将搜索范围修改为仅检查目标配置所在的那一行后，立刻成功拦截了该变异。

**判据**：当这条断言触发失败时，它具体检查的是哪一行或哪个字段？如果无法明确指出具体检查的位置，则说明该断言当前是恒真的。

**脱敏说明**：原文主要描述通用的代码审查与断言编写经验，已移除具体的项目代号、内部字段标识（A2）、内部文档路径及具体日期，改写后为通用的技术实践笔记，无高辨识度的内部信息残留。

## 拆索引与拆卷：指针及承诺形态的三个常见陷阱

<!-- 原编号 §2.199 · 脱敏风险 低 -->

**问题**：在拆分子索引或分卷管理时，因指针行的格式选择与数量承诺的标注方式不当，导致自动化校验脚本产生误报的场景。

**机制**：拆分子索引时，格式匹配规则仅识别特定的标题或标记样式（如 `**§2.N` 或 `## 2.N`），不识别表格行。全局检查会将附带中文括号数量注记的行视为已登记的承诺形态。此外，扩展自检脚本的数据源以循环读取子索引属于放宽校验条件，需通过负例来验证其有效性。

**证据**：实测（近期，一项目录索引方案）：指针行初稿标注数十至近百条括号注记，触发全局检查产生数处未登记承诺形态的误报；去除括号数字后校验全绿。删除子索引文件中的某个子条目编号，返回码 rc=1（报错提示条目独有该编号），恢复该条目后校验全绿。

**判据**：① 拆出的子索引仅保留表格行（如 `| 2.N | ... |`），禁止书写包含收录数量的卷头承诺，否则因表格行无法匹配特定格式规则会导致误报；② 任何新写行不得附带中文括号数量注记，指针行采用区间形式（如 2.1–2.90）即可，否则会被全局承诺形态检查判定为未登记而报错；③ 目录索引文件不得残留与子索引重号的编号行，否则会触发第一条的误报；④ 若扩展自检脚本数据源（如增加子索引循环读取）属于放宽校验，必须配置负例（删除一行→触发报错→恢复）以证明仍能正确识别违规。

**脱敏说明**：已将具体日期、特定方案名、精确容量对及具体条目编号替换为相对量或格式示例，判据逻辑与机制说明均未受影响，无残留可唯一定位执行的读数指纹。

## 搬移或续写时结构骨架会静默塌掉：H1、表头、分隔行三样，校验全绿也不报

<!-- 原编号 §2.339 · 脱敏风险 低 -->

**问题**：在批量搬移或续写一组 Markdown 文档时，文档的阅读结构可能在内容、计数和指针检查均正常时静默损坏。受损骨架包括 H1、表格表头和 `|---` 分隔行；尤其是把说明插入表格中间，会把表格拆成两张，使后一张表失去列义。

**机制**：骨架行具有三重隐形性：① 不被任何计数依赖——条目数依赖 `§` 行，链接数依赖 `](`，行数依赖 `wc`；② 不属于任何条目——它没有编号，因此索引与指针都不会指向它；③ 解析器仍会逐行读取——例如 `^\| 2\.` 这样的行匹配规则在缺表头的表格上照样命中。三者叠加后，“能读”“计数对”“指针可达”可以全部为真，而文档在阅读层面已经错误：缺表头的表格没有列义，缺 H1 的文档没有入口标题。代价最高的是表格被说明块从中间劈开：插入一段补充说明会把原表切成两张，后一张没有列义，而原文内容并未减少，字符数甚至可能增加。这条规则补足了既有检查未覆盖的一类结构：块级下沉关注计数位点、卷入口和承诺数，结论变更后的全文反扫关注内容层同步，拆索引或拆卷关注指针形态，先定归属关注新条目归组；本条关注搬移完成后，承载内容的结构骨架是否仍然成立，各层检查不能互相替代。

**证据**：在一次自检中，同一形态同时命中多处、数卷：四份文档完全没有 H1，直接以表格开头；另一份文档既无 H1，也无表头行，首行即数据 `2.182`，渲染时该数据会被当作表头吃掉，因而在阅读界面上直接消失；一份文档有 H1，但表头下缺少 `|---` 分隔行，导致整表无法按表格渲染；另一份文档的体量预算表被一段 `>` 引用块从中间劈开，后半三行成为无表头的第二张表。上述现场当时的五闸均为绿色。一致性检查报“一致”，限额检查各项均为绿，指针审计错指为 0，条目、索引和说明文件共数百项对齐，分组检查全数通过。修复时，四份文档补 H1，缺 H1 和表头的文档补 H1、表头及分隔行，另有一份补分隔行，被劈开的文档则把引用块移到表后；复扫数十卷为 0 问题，结构检查器返回 rc=0。检测器补验结果为：基线旧版七卷在修复前原样回放时，全部卷报出，其中多数卷缺 H1、少数卷缺表头、少数卷缺分隔，rc=1；在受检集合中删除一份文档的 H1，并删除另一份文档的分隔行后，2/2 均报出，rc=1；干净的受检集合为 0 卷报出，rc=0。由此具备阳性两证和阴性一证，“修复后为 0”不再是自证。实测汇总为多处／数卷被扫出，涉及缺 H1、缺表头、缺分隔和表格被劈开，修复后数十卷为 0；修复前后五闸状态未变，始终都是绿色。边界是：扫描器只判断骨架是否存在、层级是否跳级，不判断语义归属；“裸挂块”以文档内是否存在任何标题为准，无法判断长文档中局部段落是否缺少就近标题，这部分仍需人工阅读；目前只在 Markdown 上验证，未覆盖 HTML 或 PPT 的等价形态；样本范围为单库、单次扫描，但多处样本涵盖缺、劈、错位三种形态，并非单点巧合。

**判据**：本次是否违规，按以下 5 条判定：1. 搬移完成后必须核对骨架三样：每个文档卷有一个 H1；标题层级不得跳级，h1→h3 即为错误；每个表格块的第二行必须是 `|---` 分隔行，即首行为表头。2. 不得把“所有闸全绿、计数正确、解析器仍能读取”当作搬移已经完成；这三项与骨架是否完整无关，原文全部现场都位于这个交集中。3. 切片必须按结构单元切分，也就是按 `##` 边界切分，不得按行号切分；续写同名续片时，标题和表头必须由每一片各自具备，不能只写在第一片中。4. 向表格插入说明时，必须先退出表格再插入：`>` 引用块、代码块和小节标题都不得落在两个 `|` 行之间。5. 执行结构骨架检查器，扫描 Markdown 文档集合并检测缺 H1、跳级、裸挂块、表缺表头四类问题，期望结果为 rc=0。

**脱敏说明**：已按指纹定义替换了日期、精确容量与命中率，判据逻辑与机制描述保持原样，未引入新结论或占位符，脱敏彻底且不影响技术判据的有效性。

## 解析行的稳定身份：先看真实样本，再定「哪一段是噪声」

<!-- 原编号 §2.348 · 脱敏风险 低 -->

**问题**：为行号会漂移的追加日志计算稳定身份时，最初按想象中的格式（如「[09:36:59] 正文」）编写正则，连续三版均被真实数据否定。

**机制**：解析行的稳定身份需同时满足两个相反要求：对噪声不敏感（时间戳变化时指纹不能变），对语义敏感（发送方或编号变化时指纹必须变）。若仅关注前者，会将语义段当作噪声一并移除；若仅关注后者，残留的噪声段会导致指纹随行号漂移。判定哪一段为噪声不能依赖想象，必须基于真实样本，方括号内可能包含时间、发送方、编号或任意组合。

**证据**：反例来自真实非合成样本，实测数据为 10 行真实非合成样本。正则从初版到第四版的测试结果：初版唯一指纹 9/10，时间扰动后漂移 0/10，发送方保留失败，方括号正文保留失败；第二版唯一指纹 9/10，时间扰动后漂移 0/10，发送方保留失败，方括号正文保留成功；第三版唯一指纹 10/10，时间扰动后漂移 9/10，发送方保留成功，方括号正文保留成功；第四版唯一指纹 10/10，时间扰动后漂移 0/10，发送方保留成功，方括号正文保留成功。最初两版的碰撞具体发生在两行数据上：[11-16 05:32:56 发送端 #m5] 附件 文件快照（约八千字节）与 [11-16 11:14:38 发送端 #m6] 附件 文件快照（约八千字节），两者正文相同、仅编号不同，导致两条不同消息被合并。真实数据 10 行中发生 1 次碰撞，且碰撞情形为同一文件重复投递。真实格式为「[11-14 15:48:57 发送端 #u1] 正文」，方括号内除时间外还包含发送端和编号。

**判据**：1. 编写正则前必须先查看真实数据，明确列出方括号内实际包含的内容，禁止凭想象中的格式编写。2. 稳定身份必须通过四条断言，缺一不可：噪声扰动后指纹不变（如修改时间戳）；语义变化后指纹必须变（如修改发送方或编号）；不同行的指纹不碰撞（在真实全量数据上统计唯一值数量）；空输入不产生身份（空串的 sha1 为固定值 da39a3ee5e6b，多行空行会互相碰撞）。3. 两个版本在真实数据上输出相同不等于两版等价，必须补充构造样本以区分差异（本例最初两版在 10 行数据上逐字相同，需靠构造样本才能区分初版会移除方括号正文而第二版不会）。4. 碰撞率必须在真实全量数据上统计，禁止抽样，本例 10 行中出现 1 次碰撞，抽样无法发现。

**脱敏说明**：已删除具体日期、版本号及精确容量数，证据中的小样本比值作为判据依据保留，未改变任何判据逻辑或引入新结论。
