# 01a-阈值与对照 · 阈值要有物理依据，对照实验要同源同环境
> 本卷 6 条。判据集脱敏版：项目名、路径、内部编号已剥离；每条保留「问题／机制／证据／判据」四段与风险自评。

## 成本结构优先于绝对速度

<!-- 原编号 §2.1 · 脱敏风险 低 -->

**问题**：性能优化时往往只关注单一脚本的绝对执行速度，但调整后整体响应体验并未改善。定位性能瓶颈需要依赖分段计时实测，而非仅靠静态代码审查猜测——例如实际热点可能在某次处理中占据绝大部分耗时（从逾两分钟优化至不足两秒）。

**机制**：执行优化前，需先测量三个核心指标：1. 墙钟总时长（通过起止时间戳记录）；2. 工具与脚本耗时合计（单独计时，区分串行关键路径与并行重叠部分，当其占比低时，优先排查外部请求或资源获取环节，注意 20% 仅为本案例的排查启发，并非通用硬阈值）；3. 上下文 token（以实际计量为准，字节换算仅作明确标注的粗估）。需明确 token 占比不直接等同于墙钟时长或费用占比，不得仅凭 60% 的占比直接判定性能瓶颈。

**证据**：实测记录（本次流程）：墙钟总时长约六分钟，脚本耗时合计不足一分钟，占比为 10.4%；单次上下文 token 约三万余，其中主指令文件正文占绝大部分，占比为 89%。已作废的推断（后续复核）：先前曾由上述数字推导出“97% 的成本在读取文档、3% 在执行任务”，并声称“上下文永远是第一成本”，因缺乏同口径的费用与关键路径实测证据，该推断已作废。89% 的估算 token 占比不能推导出 97% 的成本占比，不得继续引用。

**判据**：在评估性能瓶颈时，必须先区分墙钟时长、关键路径、token 与费用，依据实测数据定位瓶颈；在没有费用实测数据的情况下，不得下达任何成本比例结论；同时，不得按 60% 的 token 占比直接判定瓶颈，也不得将 token 占比直接等同或推导为成本占比。

**脱敏说明**：日期与精确容量读数已全部替换为相对量，残留的百分比均为判据的边界说明与证据骨架，无来源指纹。

## 阈值要有物理依据：先量机制的下限，再定门槛

<!-- 原编号 §2.12 · 脱敏风险 低 -->

**问题**：闸门阈值凭手感定（例如把"数字徽标居中偏移 ≤0.5px"当作合格线），结果这套机制本身存在 1px 的量化，阈值永远达不到——闸门天天亮红，红久了就没人看，最后连真实缺陷一起放过。

**机制**：定阈值前先量出**这套机制的下限**，门槛挂在下限之上，并把理由写进脚本头部。
| 步骤 | 做法 | 产出 |
|---|---|---|
| 1 找量化源 | 找出机制里"取整/截断/最小步长"的那一层 | 量化的**周期**与**跳幅** |
| 2 量下限 | 多档分辨率各量一次；若跳幅不随分辨率缩放 ⇒ 是机制而非伪影 | 下限 = 跳幅/2 |
| 3 定门槛 | 门槛 = 下限 × 安全系数（实测 0.54 → 定 0.6；1.01 → 定 1.1） | 门槛 + 理由 |
| 4 同源同步 | 门槛值**只在脚本里定义一次**，调用方读脚本的常量或输出串，⛔ 不硬编码副本 | 改一处不漏另一处 |
本轮我自己违反过第 4 条：调用方脚本把整串 `判定(绝对 ≤1.1): PASS` 硬编码进匹配——既抄了阈值副本，又把输出格式绑死。脚本一旦改格式（它自己就改过两轮：`判定(严格 ≤0.6)` → `判定(绝对 ≤1.1)`），契约即断裂。已改为**从正本读 `STRICT` 常量、并核对脚本实际打印的阈值与正本一致**（详见 §2.18）。
另有第二个下限来源：内容总量 ÷ 容量——本轮自定「每页留白 ≤40%」，两页内容合计约 1.15 页 ⇒ 均分后每页必空 ≈42.5%，判据本身不可达（实测最好不足八成）。定判据前先把这个下限算出来；算出来高于目标，就改判据，别继续调版面（§2.17）。

**证据**：实锤（本次页面数字徽标居中实测场景）：旧严格档 0.5 / 实用档 0.8，实际可达值 1.01px。量出「浏览器端打印按 1 CSS px 取整文字基线」后，门槛改 1.1，并把"跳幅 1.07~1.10px、周期 1.00px、288/576/1152dpi 三档一致 ⇒ 非栅格化伪影"整段写进量测脚本的文件头。

**判据**：这个阈值能被"这套机制的物理下限"解释吗？解释不了，就是随手定的数字。普适结论：**闸门的红，必须意味着"世界变了"，不能意味着"我当初拍脑袋拍小了"。** 一个永远红的闸门比没有闸门更坏——它训练所有人忽略红灯。

**脱敏说明**：仅删除明确属于来源指纹的具体日期、与容量配对的精确比值，未改动任何判据逻辑、机制说明与边界要求，保留的数字均为支撑判据的核心参数与证据，无信息泄露或逻辑偏差风险。

## 将“调不动”转化为可判定结论：执行扫描实验，停止无效调参

<!-- 原编号 §2.13 · 脱敏风险 低 -->

**问题**：在参数调整过程中，修改参数后未观察到预期效果。此时需要明确：是尚未找到正确的参数组合，还是底层机制存在物理边界、导致参数根本无法产生效果？若不加分辨地持续调参，会将大量时间消耗在无法达成的目标上。

**机制**：并行执行三条证伪路径，任一路径验证成立即可终止调参。路径A（变更采样精度）：在 2~3 档不同采样精度下测量同一目标产物，若偏差跳幅不随采样精度缩放，说明是底层机制问题而非测量伪影。路径B（变更渲染属性）：开启底层渲染开关或相关属性后重新测量，若数值逐位完全一致，说明属性层面无法解决该问题。路径C（参数扫描）：在小区间内扫描参数（步长 0.2，跨越 1~2 个周期），绘制响应曲线，若曲线呈现阶梯状（微小改动无变化、跨过特定阈值才发生跳变），则证明存在量化边界。

**证据**：经三条路径全部证伪后，确认了 1 CSS px 的量化边界：分别修改 0.02、0.09、0.17、0.47 px 时结果完全无变化，修改 0.90 px 时产生 1.06 px 的跳变；平移扫描范围 0 至 1.6 px，实测周期恰为 1.00 px（0.0 与 1.0 两个位置的数值逐位相同）。

**判据**：本次是否执行了参数扫描实验？若测得的响应曲线呈现阶梯状，即判定已触及机制下限，本次调参视为无效，应停止继续调整并转入判据修正流程。

**脱敏说明**：该文档描述的是通用的参数扫描与渲染边界判定方法，未涉及特定业务系统、内部项目名称、人员身份或专属路径，核心数字均为通用技术指标，脱敏后不具备指向特定内部实体的风险。

## 对照实验必须与真件同源同环境

<!-- 原编号 §2.15 · 脱敏风险 低 -->

**问题**：在进行对比测试时，若自行构建的测试页面仅内联了基础样式，遗漏了外部链接的样式表，而核心尺寸规则恰好定义在外部样式表中，会导致实验件的尺寸表现异常，从而使整个对比结论作废。

**机制**：1. 资源清单逐条对齐：实验件与参照件必须引用同一批外部链接资源（同一批样式表与字体）。
2. 先跑基线一致性：不改动任何内容时，实验件的测量值应与参照件一致，不一致则先修复环境。
3. 一次只动一个变量：对比页面之间只允许存在一个差异。
补充控制：字体对照须逐项锁定文本、字号、颜色、轴重、OpenType特性、缩放、媒介和DPI，待测轴重为唯一自变量时其余固定。不同字形的x高与含上伸部整行高不可共用标尺，不得为通过更换分母。使用同文本多实例进行分类，当前分辨率分不开即记不可区分，不无限追值。参数与原生栅格一并留证，示例误差不升格为通用阈值。
替身（桩）亦属实验件，须与被测件同执行器、同调用形态（若使用A语言编写桩、却被B解释器调用，会导致语法错误且退出码为1，被测分支未进入），且须先返回已知值以自证调用方确实走到该处。不同处理阶段的产物不视为同源，未经前置处理的样张不能用于论证处理后的合规性。

**证据**：补上外部样式表链接后重新测试，被测件尺寸与参照件保持一致，对比实验才成立。另一例：新旧两份文档的样式差异对比显示完全一致，据此改用交叉替换样式块的方法，一次便将差异定位。实测显示，最终交付件的中性RGB残留值为0，而未经前置处理阶段的样张无法作为有效对照。

**判据**：实验件与真件的资源清单是否逐条相同？基线一致吗？变量只有一个吗？

**脱敏说明**：已去除具体文件名、内部文档路径、章节引用、修订日期以及特定脚本语言和解释器名称，场景已泛化为通用的前端样式对比测试与验证流程，无特定内部项目或系统可识别信息。

## 整轮耗时按交付边界量，异质任务不算提速

<!-- 原编号 §2.20 · 脱敏风险 低 -->

**问题**：在评估任务处理的整体耗时与效率提升时，若未严格界定计算边界，容易将异质任务的耗时或局部处理时间与整体等待时间混淆，从而得出不准确的提速结论。

**机制**：将脚本执行、模型交互往返、首条可用响应、返工处理及最终交付等阶段分别进行计时；并行处理的耗时之和不能等同于实际的墙钟耗时。在进行耗时对比前，必须对齐任务类型、输入条件与质量评估门槛，严禁使用局部耗时数据来替代用户的整体等待时间。

**证据**：实测数据表明：单一类型任务的整轮处理耗时为242.332秒，混合类型任务的用户反馈耗时为47min+，另一次修复处理耗时为1418.740秒；这三组数据不可直接用于计算提速比例。由于首条响应缺乏独立的时间戳记录，因此不报告首响耗时。

**判据**：若需得出整轮提速的结论，必须同时满足具备明确的起止事件、完成同类任务对照、保持质量水平以及排除未计入耗时段；未满足上述条件则不符合整轮提速的判定标准。

**脱敏说明**：原文主要描述通用的工程度量与计时纪律，未包含具体的项目名、人名或特定业务线信息。脱敏过程仅替换了少量可能引发具体场景联想的词汇，核心逻辑和实测数字均为通用的技术指标，难以据此反推内部敏感信息。

## 度量两端定义不一致 ⇒ 永久假红，会误伤全部历史件

<!-- 原编号 §2.123 · 脱敏风险 低 -->

**问题**：在自动化校验中，度量工具采用的计算口径与被检产物实际烘焙时使用的口径不一致，导致对同一对象的判定出现长期、稳定的失败信号。这种失败并非由产物本身的质量变化引起，而是由量具定义与被检物定义的错位造成，容易波及所有历史件，并被误判为新增缺陷或回归。

**机制**：门槛通常只记录阈值，不记录所测量的具体定义。质心、bbox 几何中心、极值、面积等口径在被检物上并不等价，当两端定义存在差异时，仅调整阈值只能让一部分样本从失败转为通过，同时让另一部分样本从通过转为失败，无法解决根本的一致性问题。修复方向应是先对齐两端的定义，而非调阈值或修改被检物坐标。

**证据**：以数字字形校验为例，门禁量使用「墨迹质心 − 填充区质心」，但被检样张按「墨迹 bbox 几何中心」烘焙坐标。在特定字号条件下，质心与 bbox 几何中心的差值（单位 uu，1uu=0.2px）呈现明显分化：数字 7 的差值远超其余数字，其余数字的差值均极小（在亚像素量级）。其中数字 7 的预测差值与实测值均在约一像素量级且符号一致；其余数字在两套口径下的差值均不超过半像素，使用同一量具均可通过。由于特定字形必然触发该量具的失败信号，导致单点恒红，与产物实际质量无关。对已交付的历史件进行反证：使用同一量具校验数十件既有件，最大偏移均不超过约一像素半，同样判定为失败，说明该状态属于既有特征，并非本次引入的回归。另一类情况涉及含随机字段的产物：同一输入运行两次，产物体积完全相同（达数百万字节量级），但 md5 校验值不同，差异仅出现在文档 ID 的第二半段（数十个十六进制字符，每次保存均会重新计算）。这并非产物变坏，而是量具与被检物定义不一致：md5 度量的是整份字节，而被检物本身包含随机字段。修复方法为固定身份，使 ID 由内容哈希决定，修复后同一输入两次产出可达到逐字节一致。补充实例：在目录条目计数场景中，`ls -ld` 输出的第二列是硬链接数，并非条目数。实测某目录下 `ls -A | wc -l` 结果为十余条，而该列显示为略多于十余条（该值为硬链接数，等于子目录数加二）。若据此误记为该数量的条目，会多出一条待查差异。正确做法是数条目时仅采用 `ls -A | wc -l`（含隐藏项）或 `find -maxdepth 1`，不读取 `ls -ld` 第二列。

**判据**：① 门槛登记必须同时写明「测的是什么定义」与「被检物按什么定义烘焙」。② 两端定义不同 ⇒ 先对齐定义再谈阈值，禁止调整阈值，禁止修改被检物坐标去迁就量具。③ 报「新缺陷」之前，先用同一量具跑既有已交付件：同样判定失败 ⇒ 属于既有状态，不得报成回归，不得据此阻塞新件；只有既有件通过而新件失败才算回归（本条限定同量具的新旧件回归归因，不否认既有缺陷的存在）。④ 反复出现的单点失败且能用字形或几何特征解释 ⇒ 记 EVIDENCE_ADJUDICATION（包含既有件对照数据），禁止修改产物，禁止调整阈值；保留原失败判定，不改写为通过。⑤ 当产物含随机字段（文档 ID、时间戳、UUID）时，哈希判据与被检物定义不一致 ⇒ 永久假红；正确修法是固定身份，禁止通过放宽判据（如改为「体积相同即通过」）来绕过。

**脱敏说明**：已将全部精确日期、版本号、容量大数与精确读数替换为相对量或量级表述，机制、判据与边界逻辑均原样保留，未新增任何原文没有的结论或数字。
