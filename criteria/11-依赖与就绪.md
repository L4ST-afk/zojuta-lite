## 修复末端故障无法挽回前期的败局

<!-- 原编号 §2.116 · 脱敏风险 低 -->

**问题**：链路上的失败点在末端，但病灶常在上游。将末端的报错修复后，症状虽然消失，但整体结果并未改善。

**机制**：在排查链路失败时，需区分症状与根因。对于控制参数，需确认其作用层级：是仅移动整体，还是能改变内部元素的相对关系。若参数仅产生整体平移，则无法改变内部相对位置，微调参数只会带来微小的相位跳变。

**证据**：在一次复盘中，为一个测试程序增加六行代码，专门处理末端触发失败的场景。末端触发失败的次数从 36 次降至 1 次，症状基本归零，但失败的总对局数只减少了 13 局，在面对较强的对手时依然无法获胜。归因结论为：败局早在前期的布局阶段就已注定。在确认控制参数作用层级的测试中，某参数通过平移变换移动整个 UI 组件，无法改变组件内部元素的相对位置；两次调整参数值，仅带来 1px 基线对齐的相位跳变，数值从 −1.41 变为 −1.27。

**判据**：① 修复失败点之前，先判断该失败是由其自身引起，还是由更早的某个决定造成的；② 验收标准以结果集的变化为准（失败用例数或失败局数的变化），不得仅以症状是否消失为准（如报错是否不再出现）；③ 若症状归零但结果未变，说明只修复了报错点，并未修复根本缺陷；④ 若败局在前期已定，需继续向上游追溯至第一个可改变的决定，不可停留在报错处；⑤ 修复前先确认控制参数的作用层级，判断其是移动整体，还是改变内部相对关系；若参数仅实现整体平移，则无法改变内部元素相对位置，微调取值只会带来微小的相位跳变。

**脱敏说明**：已全面替换或删除具体项目名、赛事名、程序代称、内部参数名及特定组件描述，改写为通用的系统排查与参数调优场景，保留了原始的判据逻辑和实测数字，无泄露内部信息的风险。

## 判端到端直连必须两端各取 NAT 类型：一端对称即否决

<!-- 原编号 §2.316 · 脱敏风险 低 -->

**问题**：在点对点直连（打洞）可行性排查中，常出现只在一端查看组网状态，发现两端同处同一虚拟组网环境且远程登录可用，就误判直连只是暂时未打通，未能及时发现其中一端为对称 NAT 导致直连实际上无解。

**机制**：打洞要求两端 NAT 都满足“同一内网端点对任意目的 IP 保持同一公网映射”。对称 NAT 按目的 IP 更换映射，对端拿到的候选地址永远无法匹配，握手必然回落至中继。而该属性仅在本端可见，对端无法获知，因此仅查询一端会得出自然且乐观的误判。

**证据**：单次实测：终端 A 为对称 NAT，终端 B 为锥形 NAT；连接探测 5/5 全部经由中继节点（延迟约三百余毫秒），明确提示未建立直连；终端 B 侧的本地防火墙处于启用且生效状态。

**判据**：1. 判定“能否直连”必须两端各取一次 NAT 类型（MappingVariesByDestIP 或等价字段），禁止只查一端就下结论。2. 任一端为对称型即直接判定“直连不可依赖”，应走中继，并将此结论写入方案；禁止将其列入“以后会打通”的待办任务。3. 必须查看实际转发路径（经中继 vs 直连），禁止用“在同一虚拟组网内或连接可用”作为直连证据。4. 中继节点需按实测延迟选择，禁止凭地理直觉选择。5. 取不到字段不等于非对称型：若在受限环境中获取网络诊断信息报凭证不可用等错误，必须在宿主终端重新获取，禁止将“读不出”判定为“锥形 NAT”。

**脱敏说明**：仅将一处精确延迟读数替换为相对量，判据逻辑、机制、边界说明及小样本证据比值均原样保留，脱敏后语义与依据不受影响。

## 迁移前先打印 sqlite_master：表名以库为准，文档里的叫法只作线索

<!-- 原编号 §2.241 · 脱敏风险 低 -->

**问题**：迁移脚本按文档写死目标表名，执行后打印出类似列不存在的错误，但实际是表名与库中真实结构不符；若直接按错误提示处理，容易把表名错误误判为列错误或空表问题。

**机制**：迁移前先执行 SELECT name, sql FROM sqlite_master 并逐行打印，以输出为准确定目标表名；区分表不存在与列不存在两类错误，查列前先判断表是否存在，避免直接查询或报错时两者输出混同；列信息核对不上时立即停止，防止误用 ALTER TABLE 在不存在的表上建空表，掩盖真实的表名错误。

**证据**：打印 sqlite_master 显示库中包含记录量从数百到一万余条不等的多张业务表及四张全文索引表。本次迁移中，两张目标表记录量分别为数千与数百条，均完成加列；两份 VACUUM INTO 备份各数百万字节；第二次 --apply 自证幂等；退出码 P1EXIT=0。复现实验中，在三种库结构场景下分别测试硬编码与先打印后分类两种写法，处置方向命中率分别为 2/3 与 3/3。

**判据**：① 任何 DDL 或迁移开工前，先执行 SELECT name, sql FROM sqlite_master 并逐行打印，目标表名必须从输出中获取，不得从文档、注释或旧脚本中获取；② 必须将表不存在与列不存在用不同输出分开，查列时先判断表是否存在（SELECT 1 FROM sqlite_master WHERE type='table' AND name=?），不得让 SELECT col FROM t 直接报错或返回 None，否则两者在打印上无法区分；③ 列信息打印后若对不上，立即停止，不得顺手执行 ALTER TABLE 对不存在的目标表进行操作，因为 SQLite 会当场创建空表，将表名错误伪装成表为空。

**脱敏说明**：仅将可唯一定位执行的精确容量读数替换为相对量级，未改动机制、判据句与边界说明，小样本命中率作为判据证据予以保留，未引入原文没有的结论或数字。

## 验收纪律：并联打勾视同未运行

<!-- 原编号 §2.335 · 脱敏风险 低 -->

**问题**：在多步骤的验收流程中，常见的反例是将一个包含多个步骤的流程拆成一张清单，然后所有步骤同时勾选“全绿”。这种操作掩盖了真实的失效场景：上游步骤缺失，但下游步骤依然显示通过，整体看似完成，实则存在无法回退的隐患。并排勾选的清单抹掉了步骤间的顺序依赖关系，导致下游的通过状态掩盖了上游的未完成状态。

**机制**：验收项之间通常存在严格的顺序依赖关系，即上游未通过则下游的测试读数无效。因此，验收必须遵循按顺序、逐项执行并各自保留独立证据的原则，严禁并排打勾。具体要求包括：每项必须固化具体的证据形态（如命令输出、读数或校验码），禁止仅写“已确认”；若上一项未通过，必须停留在该步骤，禁止先推进后续步骤再回头补测，因为补测的读数可能属于失效的旧版本；任何一次性的汇总勾选，在记录中均视同为未运行。

**证据**：在一个包含多个步骤的验收流程中，若第 1 步的前置备份未执行，而第 4 步的运行测试显示通过，这两项在清单中均呈现“通过”状态。然而，这种组合的最终结果必然是“能运行，但无法回退”。这证明了并联勾选清单会抹除顺序依赖，使得下游的通过状态掩盖了上游的未通过状态。

**判据**：针对这 N 个验收项，需明确：其中哪几项存在“上游未过则下游无效”的顺序依赖？它们是按照顺序逐项验收的，还是被并排打勾的？对于每一项，当前是否能独立、准确地复述出对应的具体证据？

**脱敏说明**：改写后移除了特定的内部文档锚点和特定业务场景的描述，内容完全转化为通用的工程验收方法论，不包含任何可追溯的特定项目或组织信息。

## 缺失统计误用成功集合做差：恒为 0 的假绿状态

<!-- 原编号 §2.266 · 脱敏风险 低 -->

**问题**：在数据写入与状态汇总的管道中，统计缺失数量时错误地使用成功集合作为分母进行差集计算，导致出口状态恒为 0，呈现虚假的成功状态。

**机制**：将成功集合作为分母去减确认数，衡量的仅仅是成功集合内部的一致性，因此计算结果永远自洽。计算缺失时必须使用计划集合作为分母，公式为：missing = (len(todo) - confirmed) + (len(adopt_todo) - adopted) + (len(rebase_todo) - rebased)。凡采用“失败即不入集合”的写法，其补集就是盲区：只能观察到成功者之间是否丢失，无法看到计划中有多少根本未成功。与其他假绿根因的区别在于：一种情况是自报数不能用自报数校验（需双观测量加独立地板）；另一种是覆盖面缺失（检查器未查询承诺型字段，导致永远 0 错）。本条针对第三种情况：检查器已执行查询且两个数均独立观测，但差集的分母选取错误，导致结果结构性恒为 0。三者的表现均为长期全绿，但根因与修法不同，不能将假绿一律归因为检查器未覆盖。

**证据**：在两个隔离测试场景（分别模拟写入全部失败与写入被拦截）中，修改分母前系统打印 tombstoned_or_fail=1，但出口码 rc 均为 0。修改分母后，这两个场景的 rc 均变为 1。两份修改前的快照运行同一套测试，rc 依然为 0，证明回归红灯是真实的状态异常，而非断言格式差异。真实运行一趟的记录为 wrote=2 confirmed=2 missing=0 rc=0，与失败场景下的 rc=1 形成可区分的状态。

**判据**：1. 计算出口码缺失数的分母必须是计划集合，严禁使用成功集合。2. 每条失败分支必须配备一个能让出口变红的用例，且该用例在旧代码上必须真实触发红灯；仅在修复后变绿等同于未测试。3. 自报的 tombstoned_or_fail=N 与出口码必须互相咬合：N>0 时，rc 必须不等于 0。若两个数值对不上，说明其中一方在报错。4. 三态出口必须互不重叠：0 表示运行完成且无缺失；1 表示运行完成但有缺失；2 表示未运行成功。严禁以输出内容是否为空来判定成败。
