## 脚本、补丁与命令的编写和执行，需要分别获得授权

<!-- 原编号 §2.38 · 脱敏风险 低 -->

**问题**：当用户提出“帮我实现某个功能”时，交付物应当是产物本身（脚本、补丁或命令清单），而不是产物已经在运行环境中执行过的状态。编写和执行是两类不同性质的行为：编写错误只影响文本，执行错误会改变运行环境的状态，例如终止进程、修改配置或覆盖文件。常见的误区是把“验证一下是否可用”当作尽责，但这实质上是在替用户做出他尚未同意的执行决定。

**机制**：在交付和执行环节遵循三条纪律：一是交付时提供 dry-run 模式，将“将要发生哪些操作”以清单形式展示给用户确认；二是在真正执行前主动询问，或由用户自行触发执行；三是若确需执行，应先在可丢弃的目标（如临时副本或测试实例）上进行，避免在用户的生产运行环境上直接尝试。

**证据**：近期的一次实测记录显示：用户需要一条命令行强制重启某桌面应用的方法，脚本编写完成后，dry-run 结果正确，确认覆盖 19 个进程且无越界匹配。随后编写者自行执行了该命令，引发四条连锁后果：一是进程被强制终止后，单例锁残留并指向已死亡的进程标识，桌面应用框架判定“已有实例在运行”，此后每次启动命令均返回 0，但实际静默失败，无进程启动、无日志输出、标准错误输出为空；二是编写者误判为应用自身损坏，先后尝试了代码签名校验、安全策略检查、注册表刷新、服务管理等一系列排查手段，直到第 4 步才读到真正有效的判据——锁文件所指向的进程是否仍在存活；三是用户在数十分钟后自行重新打开该应用才恢复正常；四是排查期间，进程匹配命令将编写者自身的命令行环境也匹配进去，输出中混入一条并非由编写者发起的重启命令，一度被误判为存在第三方操作。最终修复操作仅为一行：删除应用数据目录下对应的单例锁、Cookie 与 Socket 文件。

**判据**：这条命令或脚本，是“用户要求的交付物”，还是“我自行判断应当执行的下一步”？我所提供的验证，是在可丢弃的目标上完成的，还是在用户的实际运行环境中完成的？用户说“做”的时候，是否明确说过“跑”？

**脱敏说明**：已删除具体日期与精确时长等来源指纹，小样本计数及判据逻辑均原样保留，未改变原有语义与机制。

## 冷快照要求「所有根静止」：同根有并发写只能等，不许改根组合绕过

<!-- 原编号 §2.185 · 脱敏风险 低 -->

**问题**：在对目标执行冷快照时，工具会在运行前后对每个存储根节点进行全量 lstat 比对（检查 mode、size、mtime_ns、ctime_ns 及软链目标），若存在任何差异，工具会报错并终止。当同一根节点下存在其他并发任务时，若有 8 个进程在持续写入文件，首轮运行与预运行均会被打断而失败。

**机制**：存在两种试图绕过限制的捷径，但均不成立。其一，通过参数指定替换根节点无法排除其它根，因为根解析逻辑采用「一组默认根 + 覆盖同名键」的机制，并非整体替换集合，被监听的根依然全部存在。其二，将参数指向空目录虽能骗过监听，但在运行末尾重算主索引时，会因缺失一个根导致判定表将本该标记为 diverged 的 10 项误判为 included，从而污染全库索引。这种破坏索引的代价远高于等待。

**证据**：验收时需在运行前记录目标索引的 sha256 与 mtime，并在运行后进行比对。该运行前基准值事后无法补录，因此必须作为首要步骤执行。若无运行前基准值，则只能改用收窄证据（如本次运行仅写入了哪几个文件、其它 manifest 是否变动、判定表是否与预运行逐项一致），并需如实标注为「收窄而非等价」。

**判据**：此类工具的「静止」是前置条件，不可协商。若遇并发写入，必须采取以下操作：① 进行有界轮询等待（实测以 5 s 间隔等待 294 s，直至进程全部退出）；② 进程一旦退出立刻运行，抢占最短静止窗口；③ 严禁修改根组合、严禁强制结束其他运行中的进程、严禁使用 --force 覆盖已存在的标签。

**脱敏说明**：该文档描述的是通用的底层文件系统快照与索引机制，脱敏后去除了所有特定的业务线、项目名和内部组件指代，保留的技术逻辑属于通用的系统设计范畴，难以反推出具体的内部业务信息。

## --check 的返回点必须在第一个写操作之前

<!-- 原编号 §2.238 · 脱敏风险 低 -->

**问题**：带 --check／--dry-run 参数的脚本常被当作「只读预览」使用，但脚本内的写操作可能排在参数判断之前，导致「只看一眼差异」的操作直接修改了真实数据。

**机制**：根因：脚本中第一处写操作（git add -A 加 git commit）位于脚本靠前位置，而 if (( DRY )) 的返回点位于更靠后的位置；更麻烦的是，前置云端校验的 ABORT 逻辑也排在提交之后，使得连「报错退出」这条路径也会伴随提交副作用。修法：将 --check 的短路逻辑移到第一个写操作之前；同时注意不要让只读分支引用只有写操作执行后才存在的变量——原 DRY 分支的日志写 commit=$COMMIT，这种引用关系会诱导将判断放在提交段之后，改为 commit=NOT_RUN 即可解耦。

**证据**：实测记录：为验证镜像排除规则的改动，运行带检查参数的同步脚本，结果落地了一条提交记录，将工作区积压的大批未提交改动连同本轮改动一并提交。修后实测：运行前后 git rev-parse --short HEAD 的输出均为同一提交哈希，工作区未提交条目不变。复现记录（本地合成的同步脚本测试，使用真实 git 仓库）：A 组（先提交、后判 DRY），运行 --check 时 rc=0，输出明写「[DRY] 只看差异，未提交」并打印提交哈希；但提交数明显增加、HEAD 发生改变，表明声称与状态相反且退出码为绿；同组再跑一次，提交数继续增加。B 组（DRY 短路提到第一个写操作之前），运行 --check 时 rc=0、commit=NOT_RUN、提交数保持不变、HEAD 未变、工作区少量未提交条目原样保留；真跑一次提交数才出现增长。附带实测：只读分支里打印 commit=$COMMIT，而 COMMIT 只在提交段赋值，在 set -u 下当场报 COMMIT: unbound variable、rc=1。

**判据**：① 读脚本时先列出所有写操作的行号（git add/commit/push、rsync、rm、重定向写文件），再列 --check／--dry-run 的返回点行号；所有写操作的行号必须全部大于返回点行号。② 不要因为脚本带有 --check 参数就假定它只读。③ 只读分支的日志里不应出现「承诺这次不做的事」的变量值。④ 验收 --check 的只读特性必须读取目标状态（提交数、HEAD、工作区脏度），不要读取脚本打印了什么。⑤ 只读分支不许引用只有写路径才产生的变量，引用一次，判断就被绑定到写路径之后。

**脱敏说明**：已清除具体日期、行号与精确计数，替换为相对量级表述，机制、判据与边界逻辑保持完整，未引入新信息或改变语义。

## 转发角色不得携带自身来源头：合并采用“头优先”时，代理会静默改写真实出处

<!-- 原编号 §2.242 · 脱敏风险 低 -->

**问题**：在记录合并与同步场景中，如果转发角色也被当作客户端并携带自己的来源头，那么合并采用“头优先、报文次之”的取值顺序时，转发层填入的值会覆盖报文中携带的真实出处。数据仍有值、格式合法且不会报错，唯一的错误在于值本身是假的。

**机制**：桥接层的取值顺序是“头优先、报文次之”。第一版把本地同步程序也当作客户端处理，为其添加了自身的来源标识，结果每条从其他位置搬入的记录，其出处都被记成同步程序，而不是真实上游。正确机制是先区分产生者与搬运工：产生者负责携带来源头；搬运工不得携带自己的来源头，应将来源客户端字段置空，并把上游值放在报文里透传。

**证据**：在记录存储层新增来源标识字段后进行了实测：报文透传“上游来源标记 → 请求体来源标记”，落库为真源 ✓；本地镜像拉取后，同一条记录的来源字段仍为“请求体来源标记” ✓，说明列复制能够恢复出处；删除远端记录后执行一轮同步，输出“🗑 传播远端删除：本地清掉 1 条”，本机 count=0 ✓。

**判据**：是否违规，按以下四项核对，适用于凡“一个值有两个来源、合并规则是后者覆盖前者”的场合：① 先给角色分类再写代码：产生者（origin）才带头；搬运工（transport）必须 client=None，不携带自己的来源头，把上游值放在报文里透传。② 验收必须造一次“只带报文、不带头”的请求，确认落库的是报文值；禁止用“两条都带了、且值一样”的请求验收，因为这种请求验证的是“谁赢”，而不是“对不对”。③ 判断“值对不对”不能只看有没有值：来源客户端字段为空的检出成本很低，被覆盖成“合法但错”的检出成本极高，因此必须增加一条值域对比；存量值中一旦出现搬运工具名，如同步任务名、定时任务名或同步程序名，就应统计为覆盖事故，而不是“客户端多了一种”。④ 相关配置口子必须收在一处：端点、超时、来源头和白名单只保留在一个模块中，添加客户端等于添加一行映射；如果三个调用点各自拼接 header，那么“某个点忘了清头”将成为必然而非偶然。“头优先”是转发桥接层自身的选择，不是通用协议；如果改成“报文优先”，本条对应改为“产生者必须把值放在报文里”。判据指向的是转发层必须显式声明自己的角色，而不是某个 header 的名字。

**脱敏说明**：仅删除一个执行日期，其余读数（1 条、count=0）无法唯一定位某次执行，判据与机制完整保留，未引入新增结论。

## 判重键里不许放「会变的维度」：清理脚本沿用同一把尺，与写入脚本犯同一个错

<!-- 原编号 §2.298 · 脱敏风险 低 -->

**问题**：在本地数据镜像与源数据同步时，发现镜像行数与源数据行数存在显著差异。差异来源于同一规则被环境维度拆分为多行记录，且后续的清理操作因沿用了错误的判重标准，导致重复数据始终无法被清除，清理后数据状态毫无变化。

**机制**：旧版写入组件将当前工作目录路径作为项目标识写入数据库，导致该维度在环境变化时产生多个不同取值。而数据导入模块的判重键由规则原文和项目标识共同构成，当同一规则再次到达时，因项目标识字段的易变性，系统将其判定为新规则并创建新的记录。在后续清理阶段，清理脚本直接复用了写入脚本的判重键，由于该键包含易变维度，清理脚本计算出的重复组无法匹配到真正的重复记录，导致交集为空，清理操作失效，数据状态陷入不收敛。

**证据**：一次本地数据镜像快照显示，镜像行数较源数据多出数千行。该差异可拆解为数百组「同一规则原文、两个不同唯一标识」的记录，减去少量组（由数条极性错位记录减去个别测试样本得出）。根因在于一段时期内，旧版写入组件将当前工作目录作为项目标识，实测仅存留个位数取值，且全为特定用户的绝对路径。随后的清理操作复用了包含易变维度的判重键，清理了数千行，但上述数百组重复记录无一被清除；数日后复查，数据差异数字完全一致。修复过程中，对存量进行归一化后，判重键的有效命中情况从无一命中提升至完全命中。

**判据**：① 判重键的每个分量都必须是固定的身份标识（换环境不变）。若放入易变维度（如当前工作目录、主机名、临时路径、时间戳），同一实体会被稳定地拆分为两行，且全程不报错。② 写入前必须验证判重键的辨识力：用该键检索已知的重复对，召回率必须非零。召回为 0 说明该键无法识别需要清理的重复项。③ 清理脚本严禁直接复用写入脚本的判重键，必须先独立证明该键对当前存量数据具有非零召回率，或更换为基于原文与极性的全集对账键。④ 修复需分两步：先归一化易变维度的存量数据，再验证键是否可复用（本场景下有效命中从无一命中变为完全命中）；仅改代码不更新存量，会导致历史重复数据永久残留。⑤ 键中缺少必要维度与包含易变维度属于同类问题：若判重键仅保留规则原文而缺少极性维度，会将执行与禁止执行的记录误判为同一组。合并前需统计该键下的极性分布，否则会导致语义销毁（本场景中确有一批同文本对立极性的记录被无极性键误删）。

**脱敏说明**：所有具体日期、精确容量对及配对命中率均已替换为相对量或量级，判据逻辑与机制语义完整保留，未新增任何结论或数字。

## 脚本化向导必须使用命名参数，禁止按问答顺序喂答案

<!-- 原编号 §2.355 · 脱敏风险 低 -->

**问题**：交互向导按“先问 A、再问 B、再问 C”的顺序收集输入时，脚本化调用若按位置传入答案，例如通过管道依次发送内容，就会与问题顺序形成隐式绑定。一旦在中间插入、删除问题，或条件分支跳过某个问题，后续答案就会静默错位：值仍然存在、格式仍然合法、退出码仍为 0，但内容会被写入错误的键，且不会报错。参数定义文件的头注释也说明过这一风险。这正是后续将安装流程改为字段级 flag 的原因。

**机制**：交互问答是位置契约，脚本化调用是名字契约，两者不能共用同一个入口。应给每个必填项提供 `--key value` 形式的命名参数；脚本化模式完全不提问，非 TTY 环境自动切换到该模式并明确说明。缺少必填项时，应点名指出缺少哪个 flag，禁止写入空值，也禁止用默认值继续执行。命名参数与问题顺序解耦后，插入新问题不会导致旧脚本静默错位；新增必填项在脚本化模式下也必须显式传入。该规则只适用于需要被脚本或 agent 调用的交互式向导。纯人工使用且没有脚本化消费者的一次性问答脚本不必采用；但只要开始通过管道喂答案，就应按此规则整改。

**证据**：在近期实测中，五步安装向导可分别通过 `--yes --file --host X --dir Y` 以及平台选择参数与目标标识参数的组合脚本化跑通；`--dry-run` 只打印内容而不写盘，配置文件检查结果为“未创建”；缺少目标标识参数时，rc=2，输出会点名对应的 flag，且配置文件未生成。这三项检查均纳入离线断言，数十条全部通过。

**判据**：判断该向导或脚本是否合格：它能否在不依赖提示词顺序的情况下，仅凭参数名把每个值对应到正确的键？向问题序列中间插入一个问题后，旧的脚本化调用是否会静默改变写入的键？缺少必填项时，程序会点名指出缺少哪个 flag，还是塞入默认值继续运行？出现后者一律判为不合格。

**脱敏说明**：仅删除具体日期和精确断言条数，判据机制、边界说明和证据逻辑完整保留，指纹已清除。

## `--dry-run` 仅选对分支不算数：标志须透传至执行层，并以副作用前后计数验收

<!-- 原编号 §2.356 · 脱敏风险 低 -->

**问题**：某次干跑测试中，上层虽进入了干跑分支，却未把干跑标志一并传给底层调用；分支只决定执行路径，未将“不产生真实副作用”的意图传递到执行层。结果显示界面无异常，但一次本应仅模拟的发送操作真实发生，事后需通过管理手段撤回。

**机制**：干跑是一种端到端的意图，而非局部开关。① 分支仅负责选择执行路径，真正的安全性来源于将 `--dry-run`（或等价标志）完整透传至最外层的副作用执行器；② 验收不可仅依赖输出中出现干跑字样，须确认副作用前后计数保持不变；③ 将“标志透传”与“副作用为零”分别写成独立断言：前者检查调用日志中确实携带该标志，后者检查目标集合（如消息数、文件或行数）前后一致，二者缺一均可能产生假通过。

**证据**：修复后执行干跑调用，前后统计目标集合数量均为 118 → 118，且模拟执行层的调用日志中确实记录了 `--dry-run` 参数；两条断言纳入自动化测试脚本（80 条全部通过）。对照存在缺陷的版本：输出表现一致，但目标对象数量由 118 变为 119。
